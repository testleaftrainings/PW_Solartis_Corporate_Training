PROMPT 3 — PLAYWRIGHT FRAMEWORK ARCHITECTURE

I — INSTRUCTION

Enhance the existing Playwright project into a professional automation framework by implementing the required framework standards and architecture.

The resulting framework must be scalable, reusable, maintainable, and suitable for real-world automation projects.

C — CONTEXT

The Playwright workspace and playwright.config.ts were already created in previous steps.

Build the framework on top of the existing structure.

Do not recreate the project.

Do not remove existing working configuration.

Do not introduce unnecessary libraries or duplicate functionality.

The framework must appropriately separate application pages, tests, utilities, fixtures, configuration, data, Cucumber features, and step definitions.

E — EXAMPLES

Implement the following framework requirements.

1. PAGE OBJECT MODEL

- All application test cases must follow Page Object Model.
- Keep locators inside appropriate page classes.
- Keep page actions and reusable page-specific methods inside page classes.
- Tests should contain test flow and assertions, not duplicated application locators.
- Do not create unnecessary page classes.
- Do not create one page class containing unrelated application pages.

Preferred flow:

Test
  ↓
Page Object
  ↓
Locator
  ↓
Application

2. CUCUMBER

- Integrate Cucumber with Playwright.
- Establish a clean structure for feature files, step definitions, and supporting code.
- Keep Cucumber integration maintainable and compatible with the existing Playwright framework.
- Cucumber and Playwright should reuse the same Page Object Model wherever practical.

Preferred architecture:

Feature
  ↓
Step Definition
  ↓
Page Object
  ↓
Playwright
  ↓
Application

3. FALLBACK / RECOVERY

- Add fallback/recovery mechanisms only where technically justified.
- Fallback logic must be reusable and isolated.
- Do not hide genuine test failures.
- Do not convert failed tests into passed tests.
- Do not use excessive retries.
- Do not replace proper synchronization.
- Do not silently suppress exceptions.
- Do not use generic try/catch blocks that ignore failures.
- Document the purpose of any fallback that is implemented.

4. OOPS

Apply OOPS principles only where they provide genuine architectural value.

Use, where appropriate:

- Classes
- Encapsulation
- Abstraction
- Inheritance
- Polymorphism

Do not artificially introduce inheritance, interfaces, or abstractions simply to demonstrate OOPS.

Use private/protected members where appropriate and keep responsibilities separated.

5. ASSERTIONS

- Use Playwright's recommended assertions.
- Keep assertions meaningful and close to the validation being performed.
- Assertions must validate actual business/test requirements.
- Avoid unnecessary hard-coded waits such as page.waitForTimeout().
- Prefer Playwright auto-waiting and assertions for synchronization.

Examples:

await expect(page.getByRole("heading")).toBeVisible();
await expect(page).toHaveTitle("Expected Title");
await expect(locator).toHaveText("Expected Text");
await expect(locator).toHaveValue("Expected Value");

6. ALLURE REPORTING

- Integrate Allure reporting.
- Configure generation of Allure result files.
- Add the required npm scripts/configuration for generating and viewing Allure reports.
- Preserve the existing Playwright HTML report.
- Do not replace Playwright's built-in reporting.

The project must support:

Playwright HTML Report
+
Allure Report

7. FRAMEWORK STRUCTURE

Organize the project using a clean and reusable structure.

Use the following standard structure where applicable:

project-root/
├── tests/
│   ├── specs/
│   │   └── *.spec.ts
│   └── fixtures/
│       └── *.fixture.ts
├── pages/
│   └── *.page.ts
├── utils/
│   └── *.util.ts
├── data/
│   └── *
├── features/
│   └── *.feature
├── step-definitions/
│   └── *.steps.ts
├── support/
│   └── *
├── config/
│   └── *
├── playwright.config.ts
├── package.json
├── tsconfig.json
└── README.md

Responsibilities:

tests/specs:
- Playwright test specifications.
- Test scenarios, test flow, and assertions.

tests/fixtures:
- Custom Playwright fixtures.
- Reusable test setup and dependency injection.

pages:
- Page Object Model classes.
- Locators, page actions, and page-specific reusable methods.

utils:
- Reusable utility/helper functions.
- Do not place page-specific functionality here.

data:
- Test data.
- Avoid unnecessary hard-coded test data inside test files.

features:
- Cucumber .feature files containing business scenarios.

step-definitions:
- Cucumber step implementations.

support:
- Cucumber-specific supporting code such as hooks and world/context.

config:
- Environment/configuration-related framework code when required.
- Do not duplicate playwright.config.ts.

8. NAMING CONVENTIONS

Use consistent naming conventions.

Page Objects:
- login.page.ts
- create-lead.page.ts
- home.page.ts

Classes:
- LoginPage
- CreateLeadPage
- HomePage

Tests:
- login.spec.ts
- create-lead.spec.ts

Fixtures:
- test.fixture.ts

Utilities:
- date.util.ts
- api.util.ts
- file.util.ts

Cucumber steps:
- login.steps.ts
- create-lead.steps.ts

Feature files:
- login.feature
- create-lead.feature

Avoid inconsistent names such as LoginPage.ts, LoginPageObject.ts, loginPage.ts, or loginTest.ts unless the existing project already follows that convention and changing it would break the project.

9. PACKAGE DEPENDENCIES

Before installing any dependency:

- Check package.json.
- Check whether the functionality already exists.
- Reuse existing dependencies where possible.
- Do not install duplicate libraries.
- Use the minimum dependencies required for Playwright, TypeScript, Cucumber, and Allure.
- Do not introduce unrelated frameworks.
- Ensure installed versions are compatible with the existing Playwright version.

10. PLAYWRIGHT CONFIGURATION

Modify the existing playwright.config.ts only.

Preserve existing working configuration.

Add only required framework configuration.

Support existing requirements such as:

- browser configuration
- screenshots
- traces
- videos
- parallel execution
- retries
- reporting

Do not unnecessarily rewrite the complete configuration.

P — PERSONA

Act as a Senior Playwright Framework Architect and Senior TypeScript Automation Engineer.

Design decisions must prioritize:

1. Consistency
2. Maintainability
3. Reusability
4. Scalability
5. Simplicity
6. Testability
7. Minimal dependencies

Do not introduce architecture merely for demonstration purposes.
